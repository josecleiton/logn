Capítulo 1: O Desafio do Offline-First

O modelo de micro-aprendizagem do LogN exige um princípio rigoroso de design: o usuário não pode ser interrompido por oscilações de rede. Seja no metrô, num avião ou numa área de baixa cobertura, o jogador deve ser capaz de completar dezenas de desafios de código contiguamente (de acordo com as decisões documentadas na ADR 0002).

No entanto, manter o estado em um cliente que pode estar offline por longos períodos traz problemas clássicos de sistemas distribuídos: Como garantir 100% de integridade transacional dos pontos e XP quando o aplicativo for reconectado à internet? Como impedir ataques de duplicação (replay attacks) ou alterações maliciosas no banco de dados SQLite local no celular?

Para solucionar essas questões, foi projetada uma sincronização inspirada na estrutura fundamental do Git: um registro (ledger) imutável de eventos atrelados uns aos outros de forma criptográfica.

Capítulo 2: A Arquitetura Mini-Git: Chaining Criptográfico

A "Mente" do cliente reside no Shared Core, escrito em Rust (Crux). É no core que toda a lógica de negócios acontece de forma "Offline-First". Em vez de tentar enviar "estados finais" (como: "este usuário tem 1500 XP no total agora"), a arquitetura funciona através de um log de eventos de mutação, os chamados GameEvent.

Para assegurar que o histórico não foi corrompido, adulterado ou reordenado pelo cliente, cada evento possui um hash criptográfico que leva em conta não só seu próprio conteúdo, mas o hash do evento imediatamente anterior na linha do tempo.

Assim como os commits no Git apontam para os commits pais criando uma árvore rastreável, cada GameEvent no LogN carrega um campo PreviousHash que obrigatoriamente é parte do cálculo do seu CurrentHash. A corrente se torna inquebrável: uma adulteração num evento antigo altera seu hash local, o que mudaria o hash do evento seguinte, arruinando a validação da cadeia a partir daquele ponto.

Capítulo 3: Anatomia de um GameEvent e Cálculo do Hash

O Modelo GameEvent

No código de domínio (tanto no core em Rust quanto no struct correspondente em Go), o evento que trafega pela API é representado com os seguintes campos-chave:

type GameEvent struct {
    ID           string `json:"id"`
    EventType    string `json:"event_type"`
    PayloadJSON  string `json:"payload_json"`
    Timestamp    int64  `json:"timestamp"`
    PreviousHash string `json:"previous_hash"`
    CurrentHash  string `json:"current_hash"`
}

A Fórmula de Hash SHA-256

Quando um evento ocorre, seja offline ou online, o Core calcula o CurrentHash concatenando dados muito específicos. O Backend Go realiza exatamente o mesmo cálculo para fins de auditoria, usando o código em backend/internal/domain/sync.go:

func ComputeHash(event GameEvent, previousHash string) string {
    // 1. Concatenação estrita de dados base:
    //    PreviousHash + ID + EventType + Payload
    payloadForHash := fmt.Sprintf("%s%s%s%s", previousHash, event.ID, event.EventType, event.PayloadJSON)

    hasher := sha256.New()
    hasher.Write([]byte(payloadForHash))

    // 2. Os bytes do timestamp (int64) em formato BigEndian são inseridos na sequência
    timestampBytes := make([]byte, 8)
    binary.BigEndian.PutUint64(timestampBytes, uint64(event.Timestamp))
    hasher.Write(timestampBytes)

    // 3. A saída é a string hexadecimal da soma
    return hex.EncodeToString(hasher.Sum(nil))
}
Detalhe importante: Quando a conta é nova e não tem eventos anteriores, o "PreviousHash" utilizado é uma string com 64 zeros (0000...0000).

Capítulo 4: O Endpoint /sync: Validação Server-Side

No LogN, há uma diretriz severa de design descrita no AGENTS.md: "O Go Backend deve apenas validar esse hash, nunca recalculá-lo para reescrever o histórico".

O endpoint de entrada POST /api/v1/sync processa a solicitação em syncHandler e realiza as etapas de forma determinística e segura.

Isolamento do UserID

O corpo da requisição de sync contém um campo user_id no payload JSON. No entanto, por segurança, o Handler ignora essa informação provida pelo cliente. Ele captura o ID do usuário direto do Token JWT validado pelo sistema e sobrescreve payload.UserID = userID. Sem isso, alguém com um token legítimo poderia despachar eventos (como "desafio vencido") para a conta de terceiros forjando a identificação da cadeia.

O Processo de Verificação (ValidateSync)

Depois de buscar no banco de dados a "Top Hash" (o hash do último evento já aceito para este usuário), a função ValidateSync entra em ação:

func ValidateSync(payload SyncPayload, serverLastHash string) (bool, error) {
    currentHash := serverLastHash
    // ... ajuste de inicialização ...

    for i, event := range payload.Events {
        // Valida se o ponto de partida do lote conecta com o HEAD do servidor
        if event.PreviousHash != currentHash && i == 0 {
            return false, errors.New("force_rebase")
        }

        // Refaz o Hash e verifica se a conta do cliente bate com a realidade
        calculated := ComputeHash(event, currentHash)
        if calculated != event.CurrentHash {
            return false, fmt.Errorf("hash mismatch on event %s", event.ID)
        }

        currentHash = calculated
    }

    return true, nil
}

Se em qualquer ponto da cadeia houver falha matemática, tudo é imediatamente abortado, devolvendo HTTP 403 Forbidden e logando "sync recusado".

Capítulo 5: Tratamento de Conflitos: O "Rebase"

Como resolver a situação em que um usuário joga pelo Celular A sem internet, enquanto joga pelo Tablet B (que estava online e emitiu eventos reais)? Nesse cenário, as linhas do tempo dos dois dispositivos se ramificam.

Isso é interceptado em ValidateSync quando o PreviousHash do primeiro evento que o Celular tenta enviar não corresponde ao último hash gravado no servidor. O servidor lança um erro interno "force_rebase".

No syncHandler, a resposta devolvida ao aplicativo é um conflito (status 409):

if err.Error() == "force_rebase" {
    // ...
    writeRebaseRequired(w, serverLastHash)
    return
}

Ao captar a exigência de "Rebase", o Core do aplicativo sabe que precisa fazer pull do estado do servidor, anular os próprios hashes dos eventos ainda não sincronizados, calcular os hashes novos usando como base a hash mais recente da nuvem (o "novo HEAD"), e despachar tudo novamente (tal qual um git rebase sobre a origin/main).

Capítulo 6: Segurança e Integridade da Máquina de Estados

Esta arquitetura foi escolhida especificamente para blindar o estado da gamificação:

  • Bloqueio de trapaça via SQLite Local: Se o jogador usar um aparelho "rootado", abrir o banco de dados interno da aplicação e mudar o registro do desafio is_correct: false para true, o sistema falhará silenciosamente. O PayloadJSON será diferente, o que fará o Hash SHA-256 não ser mais igual ao hash salvo naquele evento. Quando tentar fazer sync, o Go recusará a atualização por disparidade criptográfica.
  • Prevenção de Replay e Transações Duplas: O ataque comum de "capturar e reenviar" (mandar a mesma requisição via Proxy para ganhar XP múltiplas vezes) falha porque o PreviousHash do payload que está sendo enviado só era válido naquele momento específico do tempo. Na segunda tentativa de envio, o HEAD do servidor já terá avançado, forçando rejeição com pedido de rebase. Como a regra do servidor diz que XP é calculado uma única vez ancorado em transações (através de registros constantes e user_paid_challenges), o reenvio de vitórias é barrado.

Em suma, o LogN adota um mecanismo de integridade elegante: não briga contra manipulação de dados em cliente, ele torna a manipulação criptograficamente inválida sem possuir a "chave" para revalidá-la.
